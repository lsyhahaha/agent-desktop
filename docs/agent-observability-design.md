# Coding Agent 可观测性设计提案

日期：2026-11-01。基线：main `d847ae8`；设计分支：`design/agent-observability`。
状态：方案已按用户批准实施，静态分析与提案正文保留为设计依据；当前实现与实际验收以[实现记录](agent-observability-verification.md)为准。未引入新依赖、远程遥测或额外模型请求。

## 1. 设计目标与核心判断

用户需要持续回答三个问题：Agent现在做什么？遇到什么问题、需要我做什么？结果有什么证据、哪些仍未验证？

执行可见性由真实状态证明，工具可靠性由真实调用与进程结果证明，任务正确性必须由需求对应的验收证据证明。三者不能合成一个“成功”绿勾。模型说完成、工具返回成功、构建退出码0均不能单独证明任务做对。

推荐在现有聊天执行时间线上补齐当前动作、阻塞原因和证据关联，沿用SQLite业务事实与Pino诊断。第一阶段不恢复右侧Run Logs/Trace页面，不建立第二个状态引擎，不新增全量事件溯源系统。

## 3. 正确性：把结论变成有范围的证据

每个需要验证的任务记录少量验收条件（建议最多12条），与计划分开。例如“修复取消后仍写文件”：条件A是取消后没有新写入，B是运行中进程结束，C是重启后如实显示中断。读代码任务可用源码位置与解释作为证据，不强行要求构建。

建议关系：验收条件 → 一条或多条证据 → 证据适用的工作区/版本 → 判定及限制。条件来源标注user、project或agent_proposed；模型提出的条件不能冒充用户已经确认的需求，也不为每次条件拆分弹窗。

每条证据必须包含：稳定ID、runId、关联itemId/executionId、来源、检查范围、开始/结束时间、结果、适用代码版本及完整性。结果为通过/失败/未执行/未知；代码变化后原证据可保留，但标“适用于修改前版本”。检查通过仅支持其覆盖的条件，不能自动推广到全任务。

工作区含未提交更改时单独commit SHA不足以标识版本。最小方案记录本轮结构化修改revision，并说明Shell/外部写入导致版本覆盖不完整；未经明确比较方案与批准，不自研全仓文件监视或快照系统。不能确认版本一致时，证据显示“版本未确认”，不计作当前版本已覆盖。

任务级展示用“已验证2/3项；1项未覆盖”，而不是凭模型信心输出98%正确。人工审阅与自动检查分别记录；不新增强制“确认任务完成”按钮，遵循现有DESIGN.md。语义含糊或需求未清晰时显示“缺少验收标准”。

## 4. 指标定义：先保证可解释，再讨论看板

以下为目标口径，不是现成指标。第一阶段展示单轮原始计数，跨任务聚合待有真实需求后推进。

| 指标 | 分子/分母或计算方法 | 不能推断什么 |
|---|---|---|
| 当前版本验收覆盖 | 有适用且充分证据的条件数 / 已明确条件数 | 不代表条件本身完整；0项时为不适用/待定义，不是100% |
| 验收通过情况 | 逐项通过/失败/未覆盖/版本未知，列出证据 | 不把多个条件平均成质量评分 |
| 工具执行成功率 | 成功终态的逻辑工具调用 / 已接纳且终态结果已知的调用 | 单列拒绝、未启动、未知；不能隐藏分母；轮询不重复算一次命令 |
| 命令验证结果 | 按executionId去重，exited且exitCode=0才记命令通过 | running、截断终止、取消、未知不能记通过；退出码0不等于需求通过 |
| 问题与恢复 | 独立失败原因、受影响步骤、后续恢复证据 | 局部失败被修复后不能被悄悄删除；当前无自动重试则不展示重试指标 |
| 响应与耗时 | 接纳→首个可见事实，Run墙钟时间，工具执行区间，用户等待区间 | 并行区间不能求和当Run耗时；无时间点不能补造 |
| 停止与结果可信度 | 请求取消→资源清理确认；未确认结果数量 | 发出停止请求不等于已停止 |
| 用量完整性 | Provider真实主/子模型用量；审批请求另计；缺失请求数 | Token不是任务正确性，也不是实际账单 |

跨任务成功率必须固定统计窗口、样本量、排除项、模型/版本/任务类型；没有人工或确定性验收标签就不能称为“任务正确率”。离线评测可后续单独设计，禁止借线上执行终态充当评测标签。

## 5. Tool细节：调用、进程、验证结论分层

同一exec_command可能返回running，后续多个write_stdin对应同一个executionId。UI保留原始调用审计，但命令结果只结算一次；stop_process是控制调用，不能另算一个通过的验证命令。请求失败前后是否产生副作用必须独立表达。

生命周期呈现：提出调用 → 参数校验 → 等待权限（如适用） → 实际启动 → 返回句柄或结果 → 进程终态（如适用）。拒绝标“未执行”；参数非法标“启动前失败”；执行后超时标“超时，结果需核对”，不能推断无修改。轮询结果关联原始进程节点，不创建重复命令卡片。

卡片摘要展示动词、对象、状态和耗时，例如“运行 npm run build · 进行中”。展开后按字段展示工具名、工作目录、执行环境、完整命令/路径、真实授权结果、输出、退出码/信号、截断原因和关联证据。区分用户等待与真实执行耗时；现有字段不足时明确缺失，不通过前端计时猜测进程状态。

模型说明的“为什么执行”可以展示为“Agent说明”；实际参数和结果为“执行记录”。不展示内部思维链，不把模型文本当作授权、完成或执行证据。输出为不可信文本，长路径换行、长代码局部滚动，折叠时不挂载大正文。

## 6. 前端：三层渐进展示

受影响范围为聊天顶栏、每轮ExecutionTimeline、工具详情与结束总结；右侧手动终端保留独立职责。

1. 当前状态：一行真实动作+对象+并行数量；“正在读取 agent.ts · 另有2个子分析进行中”。等待时说明“等待批准联网命令”；停止期间说明“正在停止，等待命令退出确认”。可展示距离最近事实更新的时长，但只能说“暂未收到新进展”，不能判定卡死或伪造进度百分比。
2. 过程时间线：默认保留当前动作、审批、失败和重要变更；已完成读取可折叠分组，展开仍有逐项原始记录。计划与事实视觉分开，子Agent归属父步骤，但允许并行而非伪造串行执行。致命错误或授权需求就地展开，不抢走正在输入的焦点。
3. 结果与证据：本轮执行状态、已确认修改范围、验收条件列表、验证命令真实结果、尚未覆盖项与剩余问题。点击证据定位同轮工具或文件记录；历史缺证据明确显示“不完整”。

示意（设计草图，不是已运行界面）：

```text
正在运行 npm run build                            [停止]
本轮过程
  ✓ 读取 agent.ts
  ✓ 修改 agent.ts                 [查看前后对照]
  ● 执行构建 · 已运行8秒           [参数与输出]
  ○ 验证取消链路                  计划，尚未执行

本轮执行完成
  验收：1项已有证据，1项未覆盖
  ✓ 类型兼容：构建退出码0          [查看命令]
  ? 取消后停止写入：尚未实际验证
  修改：1个已确认结构化修改；Shell变更未全面核对
```

状态覆盖：空任务引导；加载旧记录显示加载而非空；无模型/目录按现有约束说明；局部错误保留后续动作；审批拒绝保持未执行；输入等待与权限等待区分；恢复中断不自动重跑；存储失败显著标记保存异常；连接中断不猜测后台停止；无适用验证明确“未验证”。

键盘可达工具展开与证据跳转，展开按钮有aria-expanded；跳转定位目标后合理管理焦点。读屏仅播报重要状态变化，不逐token/逐秒播报。中文输入法不误触提交；用户上滚时不强制跟随；最小窗口/长中文/长命令/浅深主题均需实看。

## 7. 状态归属、存储与故障边界

沿用Runtime拥有执行事实，SQLite保存业务记录，renderer只投影，Pino保存受限诊断。新增证据放入现有持久化边界；先校验身份、范围和版本，再提交后对外确认。不能从JSONL重建“已验证通过”。不以日志写入失败阻断工具结果，但业务证据保存失败必须标不完整/保存异常，不能显示已保存通过。

协议演进优先在现有timeline与snapshot中增量增加有界字段；实现前明确旧数据兼容/迁移与构建握手。旧记录缺字段返回unknown，不从最后一条模型文字推断。验收条件和证据的文本、数组、单轮数量需有上限，超限明确拒绝/截断提示；引用只允许同授权会话和Run，renderer不得指定任意文件或日志路径。

跨重启保留未知和中断；活动进程、审批句柄不恢复。迟到回调不得修改已终结Run；取消要等待已有资源生命周期结算。重复/乱序投影沿用稳定ID和revision，不另外创建前端事实账本。

## 8. 复用方案比较与成本

推荐优先复用现有React、Zod、SQLite和Pino，不增加依赖，原因是当前目标是本机用户理解任务，已有事实链条足够承载渐进改进。外部工具不自动提供项目特定的验收语义。

候选OpenTelemetry适合未来跨进程追踪、标准化导出；需要SDK初始化、上下文传播、版本适配、采样、队列、退出flush与脱敏策略，仍需自己定义业务正确性证据。托管可观测平台还引入网络、留存、访问控制和费用。正式接入前必须核对版本、许可证、支持状态和维护情况，并按AGENTS.md推荐后等待用户批准；本轮不安装、不连接、不写替代遥测框架。

性能约束：沿用128条时间线预算与按需详情；仅状态边界持久化，不逐token写验收记录；耗时共用低频刷新，不为每卡片建计时器；不每轮扫描/哈希全仓，不默认采集原始Prompt、源码或手动PTY内容，不增加模型评审请求。当前没有性能基准，不能宣称零开销。业务记录留存增长需后续实测后定清理策略，不借此自动删除历史。

## 9. 实施顺序与验收门槛

A. 先修正表达与结果口径：按executionId去重验证、区分工具返回与进程结束；标明验证范围及Shell修改边界。保留现有协议兼容，必要变更跨Runtime/协议/持久化/renderer一并完成。
B. 增强当前动作与问题卡片：复用执行事实；结构化参数详情、等待原因、并行子分析归属和证据跳转。
C. 再增加验收条件与版本关联；先支持显式条件和既有命令证据，不自动付费调用模型裁判。
D. 有真实跨任务分析/远程运行需求后，再评估OTel或托管平台，不先建设观测平台。

实施后按DEBUG.md做受控集成和真实界面验收，不新增单元测试，不默认真实付费请求：

| 场景 | 必须观察到 |
|---|---|
| 验证命令返回running，轮询多次后退出0 | 只有一个命令结果，退出前不显示通过 |
| 验证通过后再次修改代码 | 原证据保留并标版本范围，不能无条件算当前通过 |
| 构建成功但一个需求未验收 | 显示部分已验证，无“任务全部正确” |
| 工具失败后采用其他办法完成 | 原错误保留，恢复结果有独立证据 |
| 拒绝、超时、截断、取消、清理失败 | 对应真实状态，已发生副作用不被隐藏 |
| 子分析并行、未wait失败、父取消 | 父子关联正确、无假串行、终态后不再更新 |
| 保存失败、重启、旧历史、迟到/重复消息 | 保存异常/未知可见，无隐式重跑、重复通过 |
| 最小窗口、长内容、键盘、中文输入法、读屏 | 操作可达、无覆盖、无抢焦点与高频播报 |

仅本提案：检查引用、设计一致性与git diff --check，无需构建或启动。实现阶段构建包含类型检查，构建通过不代表视觉或正确性验收。
